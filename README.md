Цель проекта: 
Создать интерактивную визуализацию, связывающую физические законы, природные явления и математические формулы в единую динамическую сеть для наглядного изучения физики.Ожидаемый результат: Веб-платформа с понятным графом связей. Кликнув на любое явление (например, короткое замыкание), пользователь мгновенно видит цепочку причинно-следственных связей: от базовых законов до финальных формул. Система автоматически формирует структурированные текстовые и графические разборы физических процессов, наглядно объясняя, как теоретические правила работают в реальных ситуациях.

Состояние проекта:
На данном этапе проект нахожиться на стадии MVP 

Выбранный стэк: 
Backend - Go
Frontend - React
DB - PostgreSQL


Детали стека: TypeScript + Vite, Cytoscape.js (граф), KaTeX (формулы); Go: chi, pgx.

## Быстрый старт

Нужны Docker, Go 1.27+, Node 24+.

**Всё в Docker** (БД + загрузка контента + приложение):

```sh
make up          # http://localhost:8080
make down
```

**Локальная разработка:**

```sh
make db          # PostgreSQL в docker на :5432
make seed        # загрузить content/*.yaml в БД (можно повторять)
make api         # API на :8080
make web         # фронтенд с hot reload на http://localhost:5173 (проксирует /api на :8080)
```

Если сначала выполнить `make build`, API сам раздаёт собранный фронтенд из `web/dist`.

**Проверки:**

```sh
make check       # валидация контента без БД
make test        # Go unit + интеграционные тесты (база physics_test) + проверка типов TS
```

## Текущее состояние MVP (на 22.10.2026)

**Статус:** рабочий MVP, проверен локально и в Docker (`make up`). Ключевой сценарий из ТЗ работает: клик по явлению показывает цепочку от базовых законов до формул и автоматический разбор.

Сейчас в системе **один общий граф, собранный вручную**. В целевом продукте граф строится автоматически по конспекту ученика (см. «Концепция продукта»). Текущий граф останется демо-графом и эталоном для проверки качества построения.

### Что реализовано

- **Контент:** раздел «Электричество», 63 узла (16 величин, 11 законов, 20 формул, 16 явлений) и 106 связей. У ключевых явлений есть числовые примеры. Контент лежит в `content/electricity.yaml` и проверяется при загрузке: ссылки, допустимые типы связей, отсутствие циклов.
- **Граф:** весь граф раскладывается слева направо (законы → формулы → явления). Клик по узлу подсвечивает всех его предков, режим «Только цепочка» перестраивает граф только по ним. Есть фильтр по типам узлов.
- **Автоматический разбор** (вкладка «Разбор цепочки»), строится по шаблону из данных графа:
  - вводный текст: исходные законы, законы-следствия, ключевые формулы;
  - причинная цепочка явлений;
  - числовой пример;
  - шаги по уровням, у каждого формула, описание и основания («Использует величину…», «Объясняется через…»). Клик по шагу центрирует граф на узле.
- **Карточка узла:** формула и единицы (KaTeX), описание и пример (Markdown), входящие и исходящие связи.
- **Навигация:** поиск, ссылки на узел (`#/n/short-circuit`), светлая и тёмная темы.
- **Инфраструктура:** миграции встроены в бинарник, `seed` идемпотентен, один Docker-образ (API + фронтенд), Makefile.

### Тесты

- Go unit-тесты: построение разбора (топологический порядок, уровни, причинная цепочка), валидация контента, в том числе реального файла из репозитория.
- Интеграционные тесты хранилища на PostgreSQL (база `physics_test`): обход предков, соседи, поиск с экранированием `LIKE`.
- Фронтенд: проверка типов (`tsc`) и линтер (`oxlint`), ошибок нет. E2E-тестов пока нет: интерфейс проверялся по скриншотам из headless Chrome.

### Известные ограничения

- Граф один и общий, построен вручную. Нет загрузки конспектов, нет нескольких графов, нет пользователей и истории.
- Разбор шаблонный: тексты собраны из готовых фраз и читаются суховато.
- Причинная цепочка показывает только одну, самую длинную ветку. У «Молнии» две причины, а видна одна; вторая есть только в шагах и на графе.
- Полный граф при открытии мелкий, подписи читаются только после зума или выбора узла.
- Нет обратного направления: нельзя посмотреть, какие явления объясняет данный закон (потомки узла).
- Нет мобильной версии: на узком экране панель просто уходит под граф.
- Дизайн технический, не прорабатывался дизайнером.
- Бандл фронтенда около 420 КБ в gzip (Cytoscape, KaTeX, Markdown), разделения на части нет.
- Нет CI и деплоя.

## Архитектура

```
cmd/api/            HTTP-сервер: REST API + раздача собранного фронтенда; миграции при старте
cmd/seed/           YAML → валидация → PostgreSQL (атомарная полная замена графа)
internal/domain/    типы узлов и рёбер
internal/content/   загрузка и валидация контента (slug, ссылки, допустимые типы связей, отсутствие циклов)
internal/storage/   PostgreSQL (pgx); обход предков через рекурсивный CTE
internal/explain/   разбор: уровни по самому длинному пути (алгоритм Кана), шаблонные тексты
internal/httpapi/   хендлеры (chi)
migrations/         SQL-миграции, встроены в бинарник
content/            граф знаний в YAML
web/                React SPA
```

### API

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/api/graph` | весь граф `{nodes, edges}` |
| GET | `/api/nodes/{slug}` | узел и его входящие/исходящие связи |
| GET | `/api/nodes/{slug}/chain` | подграф предков и разбор `{overview, causalChain, steps, levels, graph}` |
| GET | `/api/search?q=` | до 20 узлов, совпадения в названии идут первыми |
| GET | `/api/health` | проверка доступности БД |

## Модель данных и контент

Граф — направленный ациклический: ребро всегда ведёт **от основания к следствию**.

| Тип узла | Пример |
|---|---|
| `law` | Закон Ома, закон сохранения энергии |
| `quantity` | Сила тока, сопротивление |
| `formula` | $I = U/R$, $Q = I^2Rt$ |
| `phenomenon` | Короткое замыкание, молния |

| Тип ребра | Откуда → куда | Смысл |
|---|---|---|
| `formulates` | закон → формула | закон записывается формулой |
| `used_in` | величина → формула/закон | величина входит в соотношение |
| `derives` | формула → формула, закон → закон | одно выводится из другого |
| `explains` | закон/формула → явление | объясняет явление |
| `causes` | явление → явление | причинно-следственная связь |
| `defines` | закон/формула → величина | вводит величину |

Эта же модель будет использоваться для графов, построенных по конспектам: LLM заполняет именно её, поэтому валидатор и разбор цепочек переиспользуются без изменений.

Чтобы изменить демо-граф, отредактируйте или создайте `content/<раздел>.yaml` (формат описан в начале `content/electricity.yaml`), затем выполните `make check` и `make seed`. Поля `formula` и `unit` записываются в LaTeX, `body` и `example` — в Markdown со вставками `$...$`.

## Концепция продукта (целевой сценарий)

**Целевая аудитория — школьники 8–11 классов.**

```
школьник заходит → прикрепляет свой конспект (PDF / DOCX / фото страниц)
  → LLM читает конспект и строит граф знаний в нашей модели данных
  → школьник получает граф как в текущем MVP: клик по явлению → цепочка → разбор
  → граф сохраняется в истории, к нему можно вернуться
```

Заранее подготовленного графа в продукте нет: **каждый граф строится из конспекта**. Ручной проверки тоже нет — ни со стороны ученика, ни со стороны команды. Качество обеспечивается автоматически:

1. **Опора на цитату.** Каждый узел и связь, взятые из конспекта, сопровождаются фрагментом текста, на котором они основаны. Backend программно проверяет, что фрагмент действительно есть в конспекте. Элементы, которые выдают себя за взятые из конспекта, но не подтверждены цитатой, переводятся в «дополнено» (мера 2) или отбрасываются.
2. **Граф дополняется, но дополнения видны.** *(решено)* Модель не ограничивается текстом конспекта. Если в конспекте есть понятия, но не описана связь между ними (например, закон Ома и короткое замыкание), модель достраивает её из общих знаний, и граф получается связным. Связь, прямо написанная в конспекте, рисуется сплошной линией. Дополненная моделью рисуется пунктиром с пометкой «дополнено» и коротким пояснением. Так видна граница между текстом ученика и дополнениями.
3. **Цикл «проверка → исправление».** Результат проходит через `content.Validate` (типы, ссылки, допустимые связи, циклы). Ошибки отправляются модели обратно, 1–2 итерации.
4. **Проверка физики.** Отдельный проход LLM ищет явные ошибки в формулах. Найденное помечается у узла значком «возможна ошибка в конспекте», а не скрывается.

## План развития

Этапы идут в порядке выполнения. Дизайн идёт параллельным треком.

### Этап 0. Инфраструктура

- [ ] CI (GitHub Actions): `go vet`, `go test` с PostgreSQL в service-контейнере, `make check`, `tsc`, `oxlint`, сборка Docker-образа.
- [ ] Деплой демо-стенда (один VPS + `docker compose`, или любой PaaS с Postgres).

### Этап 1. Несколько графов — фундамент

Сейчас граф в базе один. Нужно хранить много независимых графов.

- [ ] Таблица `graphs(id uuid, owner_id, title, status, source_name, source_hash, created_at, …)`. У `nodes` и `edges` появляется `graph_id`, slug уникален в пределах графа.
- [ ] API переезжает под `/api/graphs/{id}/…`: `graph`, `nodes/{slug}`, `nodes/{slug}/chain`, `search`. Рекурсивный обход и `explain` не меняются.
- [ ] Текущий граф по электричеству загружается через `seed` как публичный **демо-граф** — его видно на главной («вот как это выглядит»).
- [ ] Фронтенд: страница графа по адресу `/g/{id}`, текущий интерфейс графа и разбора переиспользуется целиком.

**Готово, когда:** в базе живут несколько графов, каждый открывается по своей ссылке, демо-граф работает как сейчас.

### Этап 2. Конспект → граф — ядро продукта

- [ ] **Загрузка:** `POST /api/graphs` (multipart) → `{id, status: "processing"}`. Ограничения по размеру и типу файла (PDF, DOCX, JPG/PNG).
- [ ] **Асинхронная обработка:** очередь заданий (в первой версии — таблица заданий в Postgres и воркер в том же бинарнике), статусы `processing / ready / failed`, прогресс по стадиям.
- [ ] **Чтение:** PDF и изображения передаются LLM напрямую (отдельный OCR не нужен), DOCX конвертируется в текст.
- [ ] **Извлечение:** промпт под школьный уровень, структурированный ответ строго в нашей схеме: узлы и связи с признаком `explicit` (взято из конспекта, обязательна цитата `source_quote`) или `inferred` (дополнено моделью, обязательно пояснение). Большие конспекты обрабатываются по частям с последующим сведением дублей.
- [ ] **Автоматические меры качества** 1–4 из «Концепции продукта».
- [ ] **Не физика на входе:** если физических понятий не найдено, показывается понятное сообщение, а бессмысленный граф не строится.
- [ ] **Экономия и защита:** кэш по хэшу файла (тот же конспект не обрабатывается повторно), лимит загрузок в день, таймауты, лимит токенов.
- [ ] **Данные несовершеннолетних:** исходный файл удаляется после обработки, хранится только граф и цитаты.
- [ ] **Оценка качества:** конспект по электричеству прогоняется через пайплайн, результат сравнивается с ручным демо-графом. Метрики: доля найденных узлов и связей, доля лишних и ошибочных. Прогон повторяется при каждом изменении промпта.
- [ ] Фронтенд: экран загрузки (drag-and-drop), экран ожидания с прогрессом («читаю конспект… строю связи…»), сплошные и пунктирные («дополнено») рёбра, цитата из конспекта или пояснение дополнения в карточке, значок «возможна ошибка».

**Готово, когда:** школьник загружает конспект и через 1–2 минуты получает граф. На эталонном конспекте метрики качества достигают порога, который мы зафиксируем после первых замеров.

### Этап 3. История графов

- [ ] **Идентификация без регистрации** (первая версия): при первом визите выдаётся анонимный токен владельца в httpOnly cookie, все графы привязываются к нему. История работает в рамках браузера.
- [ ] **Экран «Мои графы»:** список с названием (LLM предлагает его по конспекту), датой, исходным файлом, числом узлов и превью графа. Открыть, переименовать, удалить.
- [ ] Эндпоинты: `GET /api/graphs` (графы текущего владельца), `PATCH` и `DELETE /api/graphs/{id}`.
- [ ] **Дополнение графа** (опционально): загрузить следующий конспект в уже существующий граф. Например, новая лекция по той же теме достраивает граф, а не создаёт новый.
- [ ] **Аккаунты** (следующий шаг): вход, синхронизация истории между устройствами, перенос анонимной истории в аккаунт при регистрации.

**Готово, когда:** ученик видит все свои прошлые графы и может к ним вернуться.

### Параллельный трек. Дизайн в Figma

Дизайн делается в Figma и может идти одновременно с этапами 1–3, чтобы к концу этапа 2 было что внедрять.

- [ ] **Экраны для дизайна:**
  - главная с загрузкой конспекта и демо-графом;

  - «Мои графы»;

  - мобильные версии всех экранов.
- [ ] **Визуальный язык графа:** стили 4 типов узлов, 6 типов рёбер, сплошные и пунктирные связи, подсветка цепочки, значок «возможна ошибка».
- [ ] **Дизайн-токены:** цвета, типографика и отступы как переменные Figma для светлой и тёмной темы. На фронтенде они ложатся на CSS-переменные (уже используются в `web/src/index.css`). Цвета типов узлов сейчас заданы в `web/src/meta.ts`, их нужно перевести на те же токены.
- [ ] Внедрение дизайна во фронтенд: перевёрстка компонентов по макетам.

### Этап 4. LLM-разбор

Связный «живой» рассказ о явлении поверх шаблонного разбора. Шаблонный разбор остаётся как fallback.

- [ ] Эндпоинт `GET /api/graphs/{id}/nodes/{slug}/narrative`, ответ стримится через SSE.
- [ ] **Опора на граф:** модель получает только узлы цепочки (с цитатами из конспекта). Новые формулы и факты вводить запрещено. Упоминания узлов пишутся как `[[slug]]`, фронтенд делает их кликабельными.
- [ ] **Промпт под аудиторию:** 8–11 класс, повествование «от причины к следствию», 150–400 слов.
- [ ] **Кэш:** `narratives(graph_id, slug, graph_hash, model, text)`, повторное открытие бесплатно и мгновенно.
- [ ] Валидатор ответа: все `[[slug]]` существуют и входят в цепочку. Без ключа API показывается шаблонный разбор.
- [ ] Фронтенд: переключатель «Рассказ / Пошагово», текст появляется по мере генерации.

### Этап 5. UX графа

- [ ] **Все ветки причин:** вместо одной линейной цепочки показывать DAG причин.
- [ ] **Пошаговый проигрыватель цепочки:** «назад / далее / авто». Каждый шаг подсвечивает узел на графе и синхронно прокручивает разбор.
- [ ] **Обратное направление:** `GET /api/graphs/{id}/nodes/{slug}/descendants` и режим «Что объясняет этот закон».
- [ ] **Удобство:** подсказка с формулой при наведении, кнопки зума и «вписать».
- [ ] Разделение бандла: KaTeX и Markdown загружать лениво.
- [ ] E2E-тесты (Playwright): загрузить конспект → дождаться графа → открыть цепочку и разбор → найти граф в истории.
